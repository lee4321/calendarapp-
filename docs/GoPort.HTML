EventCalendar — Go Port Evaluation

Feasibility, expected advantages, and an implementation route for porting the ecalendar.py CLI and the event-data importers to Go. GUI (slint_ui/) and TUI (tui/) are out of scope. Prepared 2026-08-01.

Settled decisions. These are assumed throughout and each one removes risk that an unconstrained port would carry:

  • Output need not be byte-identical. The Go port must be correct and visually equivalent, not a bit-for-bit reproduction.
  • Generator scripts are dropped. Event data arrives as CSV/XLSX files through the normal import path.
  • Holidays are imported at build time into calendar.db, not resolved at runtime.

With these in place there are no high-risk items left in the port. What remains is volume, not difficulty.

Why port at all — expected advantages

All figures below are measured against the current implementation on this machine (Apple silicon, Python 3.14, -th default), not estimated.

1. Distribution — the strongest case

The tool currently requires Python 3.13+, uv, and 13 dependencies. Pillow is the fragile one. Its text metrics depend on libraqm/HarfBuzz being compiled in, and that is an optional Pillow build feature. It is present here (features.check('raqm') == True), but that is not guaranteed elsewhere — and on a Pillow built without it, getlength() silently stops applying GPOS kerning. Text then measures roughly 1.7% narrower than the layout engine expects, and every downstream placement shifts. No error is raised; the calendars are just subtly wrong.

A Go binary with shaping compiled in eliminates that entire failure class. Combined with //go:embed for the 18 theme YAMLs, the 138 fonts, and calendar.db, the result is a genuinely single-file tool at roughly 40–60 MB. For a generator people run occasionally, "download one file and run it" versus "stand up a Python environment" is a categorical difference rather than an incremental one.

Profiling the 5-year render surfaced something more interesting than language overhead:

5149  0.274s  _sqlite3.connect
5149  0.264s  sqlite3.Cursor.execute
5149  0.064s  sqlite3.Connection.close

5,149 separate database connections — about 47% of the runtime. _get_connection (shared/db_access.py:186) opens and closes a fresh connection per query. A Go port with a pooled *sql.DB fixes this incidentally, but it is fixable in Python in an afternoon for a tiny fraction of the porting effort. It should not be counted as a Go advantage. Fix it first, then re-measure the baseline this comparison rests on.

The genuine language-level wins in that profile are arrow (0.22s cumulative in arrow.range, 0.11s recompiling format regexes) against Go's stdlib time, and interpreter overhead across 219k getattr and 418k isinstance calls. A Go version should land near 40–80 ms per render — call it 6–10×. Real, but starting from 0.5s, so it changes interactive feel rather than making anything newly possible.

One earlier concern deserves downgrading: the O(n²) shaping in glyph_cache.py costs only 0.064s here. Still worth fixing during the port, but it is not a hotspot at realistic calendar sizes.

3. Batch generation — where the speedup compounds

27 renders take 11.4s serially, each paying the full ~140 ms startup. Go removes the startup entirely and makes parallelism nearly free — goroutines over a work queue would bring that batch near 1s. If calendar sets are generated (per-team, per-quarter, all-themes), this is where the difference is felt rather than merely measured.

4. Type safety where the codebase is weakest

The 521-field config with 367 theme mappings applied via setattr is the most error-prone surface in the project, and it currently fails soft — theme_engine.py:958 catches TypeError/ValueError and logs a warning. A mistyped theme key does not error; it silently does nothing. With codegen and a typed struct that becomes a build failure. Given that the CLI-beats-theme precedence bug (8796123e) lived in exactly this machinery, compile-time enforcement is worth something concrete.

5. Reproducibility

Two sources of run-to-run variance disappear: holiday data stops depending on the installed holidays version (from the build-time import decision, which is language-independent), and text metrics stop depending on how the local Pillow happened to be built (which is specific to leaving Python).

The cost that sits outside the port scope

The GUI (slint_ui/) and TUI (tui/) are excluded from the port, but they do not stop existing — and a Go core breaks a coupling neither obviously advertises. Both invoke the calendar by subprocess, which is language-agnostic and keeps working. The problem is that both build their UIs by introspecting the live argparse parser:

# slint_ui/ecalendar_app.py:239 and tui/spec.py:166
import ecalendar
parser = ecalendar._create_argument_parser("ecalendar_preview.svg")
sub_action = next(a for a in parser._actions
                  if isinstance(a, argparse._SubParsersAction))

They walk parser._actions so every new CLI flag appears in the UI automatically. A Go binary has no argparse to introspect, so both front-ends would fall back to hand-maintained flag lists.

The fix is straightforward and arguably an improvement: have the Go binary expose a spec --json subcommand that dumps its flag tree, and point both UIs at that. It is more robust than reaching into argparse's private _actions API, which is fragile across Python versions regardless. Worth planning for rather than discovering late.

Summary

The case for Go is distribution and deployment robustness first, type safety on the config surface second, and performance a distant third — with the caveat that the largest performance number measured here is a Python-side bug fixable without porting anything.

If the goal is to ship a tool that runs without a Python environment and never silently mis-measures text because of how a dependency was built, that justifies 50–65k lines of Go. If the goal is primarily speed, fix the connection churn first and re-measure before committing.

Text and font handling

Text measurement

Every layout decision flows through string_width() → PIL.ImageFont.getlength(). What that actually does, measured on this machine:

InstrumentSerif-Italic @ 9pt, "Wednesday 28"
  PIL getlength (whole string): 44.46875
  sum of per-char getlength   : 45.203125
  raw hmtx × 9/upm            : 45.207

Pillow here is built with libraqm/HarfBuzz (features.check('raqm') == True, freetype 2.14.3), so getlength does full HarfBuzz shaping with GPOS kerning and quantizes to 1/64 px (26.6 fixed point). 44.46875 = 2846/64.

Use github.com/go-text/typesetting — a genuine Go port of HarfBuzz, pure Go, no cgo. With byte-identity dropped there is no reason to consider cgo bindings to HarfBuzz/FreeType, and no reason to replicate the 26.6 quantization; correct kerned advances are sufficient.

The residual risk is not exactness, it's magnitude. Naive hmtx scaling (skipping shaping entirely) is off by 0.74pt on a 12-character string, which is enough to change where fittext() truncates and to overflow day boxes. So real shaping is required; matching it to the last 1/64 px is not.

Fix the O(n²) shaping while you're there. glyph_cache.py:152 computes each character's position with getlength(text[:i+1]) — it reshapes the string once per character. In Go, do one shaping pass and read per-cluster advances. This is faster, simpler, and more correct; the only reason not to would have been byte-identity, which no longer applies.

Glyph outline extraction

renderers/glyph_cache.py uses fontTools SVGPathPen to emit path d attributes. x/image/font/sfnt gives you segments (SegmentOpMoveTo/LineTo/QuadTo/CubeTo), so you write a ~60-line pen.

This would have been risky under byte-identity, since SVGPathPen's exact command letters, implicit-command elision, and number formatting would all have needed reproducing. That requirement is gone — the paths only need to describe the same curves. Verify by rasterizing a page from each implementation and comparing images, not strings. Note that sfnt reports quadratic segments for TrueType outlines; emit them as Q rather than converting to cubics, and keep the same translate(x,y) scale(s,-s) transform convention so the Y-flip stays in one place.

Holidays — build-time import

Python's holidays package has no Go equivalent worth using. It covers 150+ countries with a category model that db_access.py:98 depends on: it probes supported_categories, unions public+government into the shaded non-workday pool, then layers optional/half_day/unofficial as title-only entries. github.com/rickar/cal/v2 covers ~30 countries with no category concept.

Resolved by moving holiday resolution to build time. Concretely:

  • A Python generator materializes a holidays table into calendar.db — (daykey, displayname, country, category, nonworkday) — over a generous year range, applying the union and precedence rules that _load_country_holidays currently applies at runtime.
  • The Go binary reads that table exactly like it reads specialdays, colors, and patterns. load_python_holidays() becomes an ordinary query.
  • Python remains a build dependency; the shipped binary has zero runtime dependencies.

Two benefits beyond making the port possible. Holiday data becomes reproducible — today the same command run a year apart can produce different calendars because the installed holidays version changed. And it becomes inspectable, since holidays land in the same database as every other reference dataset, queryable with the existing tooling.

Two details to settle when building it: the year range to materialize (generating well past any plausible calendar range costs almost nothing — the table is small), and whether to keep the --country filter dynamic. Keep it dynamic: materialize all countries you care about and let the Go side filter by the country column, which preserves current CLI behavior exactly.

Dropped: generator scripts

load_generator_script() loaded an arbitrary user-supplied Python file via importlib, called its generate_events(), and used inspect.signature to decide which keyword arguments that function accepted. A compiled Go binary cannot do any of that, and it is now out of scope. Removing it takes with it:

  • load_generator_script (40 lines), call_generate_fn (52), import_generated_events (137)
  • The --script, --start-date, --end-date, and --param CLI options and their dispatch in main() (~60 lines)
  • importers/generators/sample_generator.py (137 lines)

About 430 lines, and with them the only genuinely un-portable construct in the codebase. Anything a generator produced can be written to CSV and fed through the normal file-import path, so no capability is lost — only the convenience of doing it in-process. Worth a line in the changelog and a note in USER_GUIDE.md, since --script is currently documented.

What ports cleanly

pandas is barely used. Despite being the heaviest dependency in pyproject.toml, the entire surface is:

  • read_excel / read_csv in common.py:269 — one function, read_file()
  • notna / isnull — null-ish checks on cell values
  • DataFrame as a row container, iterated row-wise and immediately converted to dicts

No joins, no groupby, no vectorized computation. In Go this becomes excelize for .xlsx, encoding/csv for CSV, and a []map[string]string row model. Dropping the generator path also removes the one place a DataFrame crossed an API boundary, so pandas leaves the design entirely rather than being emulated.

The null-ish checks become explicit empty-string tests, which is clearer than pandas' NaN semantics — and worth being deliberate about, since pandas silently coerces an all-integer column to float and turns blanks into NaN. The Go version will not reproduce that and should not try to.

The rest of the framework is straightforward: SHA-256 file hashing for duplicate detection, an import_history / import_sequence bookkeeping pair, transactional inserts, and --list/--remove operations keyed by import ID. COLUMN_MAPPING in import_events.py:89 (case-insensitive source-column → DB-column aliasing) is a plain map. The schema migration in ImportDatabase._migrate_schema is ALTER TABLE statements guarded by column existence checks.

Date parsing still needs care

Dropping generators does not remove the dateutil requirement. convert_date() (common.py:190) runs every date cell from every imported file through dateutil_parse, which accepts M/D/YYYY, M/D/YY, YYYY-MM-DD and much else. Go has no equivalent, so replace it with an ordered list of candidate layouts tried in turn.

Two behaviors in that function to carry across deliberately: two-digit years rely on dateutil's century inference, and a parse is rejected when the resulting year is under 1950 — a sentinel for Excel's 1899/1900 epoch leaking through. Both are load-bearing for real spreadsheets and neither is obvious from the signature. process_dates() just above it also swaps reversed ranges and mirrors a missing side; port it as written.

The theme engine needs a design decision

theme_engine.py:954 is setattr(config, field, value) over a 367-entry dict[tuple[str,str], str], against a 521-field dataclass. Same pattern in _CLI_CONFIG_OVERRIDES in cli/config_assembly.py. Three ways to handle it in Go:

  1. reflect + struct tags — closest translation, keeps the map-driven design, but you lose compile-time safety on exactly the thing that's already subtle (the CLI-beats-theme precedence fixed in commit 8796123e).
  2. Code generation — declare fields once in YAML/TOML, generate the struct, the theme map, and the CLI override table. Best fit: the mapping is data, and codegen makes it typed data. This is what I'd do.
  3. map[string]any config — closest to Python's dynamism, worst Go. Don't.

Note the two-pass apply (theme → setfontsizes → theme again → re-assert CLI) in ecalendar.py:672-696. That ordering is load-bearing and non-obvious; port it literally and let tests/test_cli_theme_precedence.py guard it. Config resolution is one place where exact equivalence is worth enforcing even though pixel output isn't — dump the resolved config as JSON from both implementations and diff, since a divergence there is a logic bug rather than a rendering difference.

Other porting notes

  • vendor/labella/vpsc.py (428 lines) is a variable-placement-with-separation-constraints solver — float-sensitive numerics driving timeline/PIT label placement. Port mechanically and compare node positions numerically. Exact float agreement isn't required, but the solver has convergence behavior that's easy to break by "tidying" it; resist.
  • argparse behavior gaps. allow_abbrev defaults to True, so --headerl currently resolves to --headerleft. Cobra/pflag won't. Decide whether that's a regression worth caring about. The per-view option gating (_shade_views etc. in cli/args.py) and @file expansion (args.py:67) are already hand-rolled and port directly.
  • getattr(x, name, default) appears 112 times in the renderers. Most are defensive reads of possibly-unset config fields and vanish against a fully-populated Go struct. Audit each anyway: a few encode real "did the theme set this?" logic, which needs an explicit pointer-or-sentinel representation.
  • SVG attribute ordering no longer matters. drawsvg emits keyword arguments in declaration order, which the byte-exact corpus guard depended on. Without that constraint, Go map iteration order is harmless — though ordered attribute slices are still worth using to keep your own diffs readable between runs.

Suggested approach

Port bottom-up, comparing against the Python implementation at each layer:

  1. Text metrics spike. Measure a few thousand strings across the fonts in use with go-text/typesetting and compare against a Python dump of getlength. Not a go/no-go gate — the goal is to confirm agreement is within a fraction of a point so layout decisions land the same way, and to find any font in fonts/ that shapes badly.
  2. Holiday materialization. Write the build-time generator and the holidays table first: it is small, it unblocks every date-aware code path, and it can land in the Python codebase immediately — the existing runtime can read the table too, which validates the data before any Go exists.
  3. Foundation: SQLite access, config struct + codegen, YAML theme loading, date/format utilities, SVG emitters. Validate the theme engine by diffing resolved-config JSON dumps.
  4. Importers. Good next target: self-contained, no font or layout dependencies, and it exercises the DB write path plus the CLI framework end-to-end.
  5. One visualizer end-to-end — text-mini (402 lines, no SVG, no glyph paths) to prove the data pipeline, then mini for the first real SVG comparison.
  6. Remaining visualizers, easiest first: candybar → weekly → compactplan → blockplan → pit/timeline (labella last).
  7. Excel subcommands and the listing/sheet subcommands.

Steps 1 and 2 are independent of each other and of everything downstream, so they can run in parallel or in either order.
