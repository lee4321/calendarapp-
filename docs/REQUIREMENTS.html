EventCalendar — Functional Requirements Specification

A capability-oriented description of the calendar / schedule visualization generator.
Subject: ecalendar CLI and supporting modules Application version: 26.06.18.0 Document date: 2026-06-22 Basis: reverse-engineered from source
This document describes what the system does (its observable functional capability), independent of how the code is organized. Requirements use shall for mandatory behavior. Each requirement carries a stable identifier (e.g. FR-VW-03) grouped by capability area.

1Product Scope & Outputs

The system generates highly customizable calendars, timelines, and project plans from event data held in a SQLite database, plus a family of utility outputs for inspecting available resources.

FR-GN-01
The system shall generate calendar and schedule visualizations from event data stored in a SQLite database.
FR-GN-02
The system shall produce output as scalable vector graphics (SVG) for graphical views, plain text for the text-mini view, Excel workbooks (.xlsx) for spreadsheet views, and CSV for data export.
FR-GN-03
The system shall offer the following primary visualization commands: weekly, mini, mini-icon, candybar, text-mini, timeline, pit, blockplan, and compactplan.
FR-GN-04
The system shall offer the spreadsheet commands excelheader and excelblockplan, and the data-export command exportdata.
FR-GN-05
The system shall offer resource-inspection commands (themes, fonts, papersizes, patterns, icons, colors, palettes) and visual preview-sheet commands (fontsheet, iconsheet, patternsheet, colorsheet, palettesheet).
FR-GN-06
The system shall write all generated artifacts into a local output/ directory, creating it if absent.Any directory component supplied by the user in an output filename is discarded as a path-traversal safeguard; only the base filename is honored.
FR-GN-07
When no output filename is supplied, the system shall derive a default name from the command and a timestamp (e.g. weekly202606221040.svg, text-mini…​.txt).
FR-GN-08
The system shall be operable without a graphical environment as a self-contained command-line program, producing files on disk and progress/diagnostic text on the console.
FR-GN-09
A single database shall be able to drive every output type, so the same event data can be presented as a grid calendar, mini calendar, timeline, plan, spreadsheet, or CSV without re-entry.

2Command-Line Invocation

All capability is reached through a single subcommand-based command-line interface.

FR-CLI-01
The system shall require a subcommand and shall reject invocation with no subcommand.
FR-CLI-02
Each visualization/export command shall accept an optional start date and end date as positional arguments in YYYYMMDD format.
FR-CLI-03
The system shall support reading arguments from one or more argument files referenced as @filename, including nested references up to a fixed depth limit.
FR-CLI-04
When expanding argument files, the system shall drop blank lines and comments (full-line and trailing "# " comments) while preserving inline tokens such as hex colors (#FF0000).
FR-CLI-05
The system shall provide a help <subcommand> command that prints argument help plus runtime-resolved valid values (weekend styles, paper sizes, themes, fiscal types, icons, fonts, colors, template variables, etc.) relevant to that subcommand.
FR-CLI-06
The system shall accept a database path via --database (default calendar.db) on every data-driven command.
FR-CLI-07
The system shall validate that the selected database path exists and is a regular file before use, emitting a clear error otherwise.
FR-CLI-08
The system shall group each command's options into labeled help sections (e.g. Database, Output, Layout, Header/Footer, Watermark, Content Filtering, Week Number, Fiscal, Logging) so the option surface is discoverable.
FR-CLI-09
The system shall share option definitions across applicable commands so semantically identical options behave identically across views.
FR-CLI-10
The system shall reject mutually inconsistent option combinations with actionable messages (e.g. icon-sheet pagination sub-options used without enabling pagination).

3Date Range Determination

FR-DT-01
The system shall validate that supplied start/end dates are well-formed YYYYMMDD values and report a friendly error when they are not.
FR-DT-02
When the end date precedes the start date, the system shall transparently swap them.
FR-DT-03
The system shall adjust the requested start and end dates outward to whole-week boundaries according to the selected weekend style — work-week styles snap to Monday/Friday, Sunday-start styles snap to Sunday/Saturday, and Monday-start styles snap to Monday/Sunday.
FR-DT-04
The system shall support five weekend styles selectable per view: 0 work-week only, 1 full week / Sunday start, 2 half weekends / Sunday start, 3 full week / Monday start, 4 half weekends / Monday start.
FR-DT-04b
The weekend style shall govern the day-column count and weekday ordering of the calendar grids in addition to the date-range snapping.
FR-DT-05
The system shall compute the calendar duration and number of weeks spanned by the adjusted range for use by layout engines.
FR-DT-06
The system shall allow the set of non-working weekdays to be specified explicitly via --weekend-days (comma-separated ISO weekday numbers 0–6), validating range and uniqueness.
FR-DT-07
The system shall retain the original user-supplied dates separately from the week-adjusted dates so both are available to metadata and template expansion.

4Data Sources & Event Model

Calendar content is drawn from several tables in the SQLite database plus a live government-holiday data source.

FR-DM-01
The system shall retrieve all events whose date span overlaps the adjusted calendar range, including multi-day events that begin before or end after the range.
FR-DM-02
The system shall recognize the following event attributes: task name, status, priority, WBS code, rollup flag, milestone flag, percent complete, effort, duration, start/end dates, early/late date bounds, predecessors, resource names, resource group, notes, icon, color, and tags.
FR-DM-03
The system shall classify an event as a single-day event when its start equals its end, and as a multi-day duration otherwise.
FR-DM-04
The system shall read company special days (with non-working-day flag, day color, pattern, pattern color, icon, and tags) and apply them as day decorations, degrading gracefully when optional columns are absent.
FR-DM-05
The system shall load named icons (SVG markup with alternative-name aliases), named colors (RGB → hex), color palettes (ordered color lists), day-box patterns (tileable SVG), and paper sizes (with portrait/landscape canonicalization) from the database.
FR-DM-06
The system shall recognize a defined set of event statuses (active, draft, cancelled, archived, on-hold) and treat unknown statuses as if active.
FR-DM-07
Event retrieval shall include any event whose span overlaps the range, i.e. events starting within the range and durations that begin before and/or end after it, so partially-visible durations are available for clipping.
FR-DM-08
The system shall normalize event records into a consistent internal model (deriving each item's effective start/end, duration-vs-event classification, and milestone/rollup booleans) so all views consume a uniform event shape independent of source column naming.
FR-DM-09
The system shall index events onto every day they span so day-oriented views can look up events by day key, while continuous-axis views consume the events by their start/end dates.
FR-DM-10
The system shall resolve icon references by name or alias to SVG markup, including backward-compatible resolution of numeric icon identifiers.

5Content Filtering

A single, authoritative filtering policy governs which events appear, applied identically across every visualizer and the data exporter.

FR-FL-01
The system shall exclude holiday rows from the event stream (they are rendered as day decorations, never as event entries).
FR-FL-02
The system shall filter events by status, defaulting to active only, and shall accept --status with a comma-separated list or all to disable status filtering; unknown status values are rejected.
FR-FL-03
The system shall optionally exclude single-day events (--noevents) and/or multi-day durations (--nodurations).
FR-FL-04
The system shall optionally exclude fully complete items (--ignorecomplete, percent complete = 100%).
FR-FL-05
The system shall optionally restrict output to milestones only (--milestones) or to rollup entries only (--rollups).
FR-FL-06
The system shall filter events by Work Breakdown Structure code via --WBS, supporting comma-separated tokens, ! exclusion, dot-separated segments, * single-segment wildcard, ** multi-segment wildcard, and implicit prefix matching.
FR-FL-07
The system shall provide an --empty option that produces a structurally complete output containing no events.
FR-FL-08
The system shall optionally append event notes to displayed event names (--includenotes) on views that support it.
FR-FL-09
The filtering policy shall be applied identically by every visualizer and by the data exporter, so a given range and option set yields the same item set across all outputs.
FR-FL-10
The filters shall compose conjunctively (holiday exclusion, then status, completion, milestone/rollup, WBS, then event/duration type), and the compiled WBS filter shall be cached per filter expression for efficiency.

6Holidays & Non-Working Days

FR-HOL-01
The system shall obtain government holidays from a live holiday data package for the calendar's year span, rather than requiring them to be stored in the database.
FR-HOL-02
The system shall accept one or more ISO 3166-1 alpha-2 country codes via --country (e.g. US or US,CA,GB), defaulting to US and CA when omitted.
FR-HOL-03
The system shall treat public and government holidays as non-working days (shaded), and treat optional / half-day / unofficial holidays as informational titles without shading.
FR-HOL-04
The system shall deduplicate holidays by date within a country, giving public-category names precedence over government-category names on shared dates.
FR-HOL-05
The system shall skip unsupported countries with a warning rather than failing the run.
FR-HOL-06
The system shall determine, per date, whether it is a non-working day from either government holidays or company special days.
FR-HOL-07
The system shall tag each loaded holiday with its country and a country-derived icon, and shall allow holiday lookups to be filtered to one or more countries.
FR-HOL-08
The system shall resolve a display title and icon for a given date from government holidays first and then company special days, so day-decoration consumers have a single resolution path.
FR-HOL-09
Company special days shall contribute their own non-working-day flag, fill color, pattern, pattern color, icon, and tags to day decoration independently of government holidays.

7Calendar Visualizers

The calendar views (weekly, mini, mini-icon, candybar, text-mini) render the same filtered event, holiday, and special-day data through distinct layouts. They share a common day-classification and styling model, then differ in how each day and its events are drawn.

7.1   Shared day-cell styling modelALL CALENDAR VIEWS
FR-VW-01
The calendar views shall classify each visible day into a set of classes — at least workday, weekend, non-working day, federal/government holiday, and company holiday — for use in conditional styling.
FR-VW-02
The calendar views shall resolve each day's visual treatment by layering, in order, fiscal-period styling, government holidays, company special days, on-day events, and theme style rules, with later layers overriding earlier ones on conflicting properties.
FR-VW-03
The system shall support theme style rules that conditionally restyle days and/or events. Day-level conditions shall include federal_holiday, company_holiday, nonworkday, workday, weekend, and a specific date or date range.
FR-VW-04
Event-level style-rule conditions shall include task name, notes, resource group, resource names, WBS, priority (exact / min / max), percent complete (min / max range), milestone, rollup, event type (event vs. duration), color, and icon.
FR-VW-05
A matched style rule shall be able to override fill color and opacity, stroke color/width/opacity/dash, decorative pattern (name, color, opacity), icon and icon color, text alignment, and per-text-element font/size/color/opacity.
FR-VW-06
When non-active statuses are surfaced, the calendar views shall visually dim events by status (e.g. draft, on-hold, cancelled, archived progressively more faded) without altering layout, so status is distinguishable at a glance.
FR-VW-07
Each visualizer shall validate the configuration it receives and emit warnings (without aborting) for options that do not apply to it.
7.2   Weekly grid viewweekly
FR-WK-01
The weekly view shall render a continuous grid of day boxes spanning the adjusted date range, one row per week, with column count and weekday order determined by the weekend style.
FR-WK-02
Each day box shall display a right-aligned day number, an optional month indicator/name, a background fill (by month, fiscal period, holiday, or rule), and optional pattern/hash decoration.
FR-WK-03
Each day box shall display holiday and company-special-day titles and icons, and shade non-working days using the configured holiday colors and opacities.
FR-WK-04
The weekly view shall place single-day events as text within their day box, supporting an optional appended notes line and an optional event icon.
FR-WK-05
The weekly view shall render multi-day durations as horizontal bars spanning the covered days, breaking the bar across week-row boundaries and continuing it on each subsequent row.
FR-WK-06
When a duration extends beyond the visible range, the weekly view shall indicate continuation with left/right arrow icons at the clipped edge.
FR-WK-07
For durations of sufficient length, the weekly view shall render notes inline with the name; for shorter durations with notes enabled it shall use a double-height bar with name and notes on separate rows.
FR-WK-08
The weekly view shall order event/duration placement within a day by a configurable precedence among milestones, events, and durations, with a secondary sort by priority or alphabetically.
FR-WK-09
When a day cannot fit all of its items, the weekly view shall mark the day with an overflow indicator and, when --overflow is set, emit a separate overflow page listing the items that did not fit.
FR-WK-10
The weekly view shall optionally render a week-number label per week row and fiscal period labels on fiscal-period-boundary days.
FR-WK-11
The weekly view shall support text shrink-to-fit so event names that exceed the available width are reduced or truncated rather than overflowing the box.
7.3   Mini and mini-icon viewsmini · mini-icon
FR-MN-01
The mini view shall render one compact month grid per calendar month in range, arranged into a configurable number of columns (months per row) and rows (or auto-derived from the range).
FR-MN-02
Each mini month shall render a month title (with a configurable format string), a weekday header row, and a 7-column day grid honoring the weekend style's week-start.
FR-MN-03
The mini view shall optionally show or hide leading/trailing days from adjacent months, rendering adjacent-month days dimmed.
FR-MN-04
The mini view shall optionally draw grid lines between day cells and an optional week-number column.
FR-MN-05
The mini view shall convey day-level information through cell treatments including: background shade, bold/outlined/strikethrough day numbers, a box or circle around the number, an icon replacing or appended to the number, and pattern/hash decoration.
FR-MN-06
The mini view shall circle milestone days, color day numbers by resource group, embolden high-priority days, and display event/holiday icons drawn from the day's events and holidays.
FR-MN-07
The mini view shall render multi-day durations as color bars beneath the day cells they span, with an optional label.
FR-MN-08
The mini view shall optionally emit a companion event-details SVG (--mini-details) listing the events behind the mini calendar.
FR-MN-09
The mini-icon view shall render the mini calendar with day numbers placed on a selectable icon set (squares, dark squares, circles, dark circles, squircles, dark squircles).
FR-MN-10
Mini-family views shall optionally shade fiscal-period day backgrounds and place fiscal period labels on period-start days when a fiscal calendar is enabled.
7.4   Candybar year-strip viewcandybar
FR-CB-01
The candybar view shall render a vertical strip with one row per ISO week and one cell per weekday, reusing the mini view's day-cell styling.
FR-CB-02
The candybar view shall render a merged month-name box alongside the weeks of each month, with configurable side (left/right) and configurable label rotation (e.g. vertical reading-up).
FR-CB-03
The candybar view shall support fixed or auto-fit row height and a fixed or square day-cell width.
FR-CB-04
The candybar view shall optionally suppress weekend columns, optionally shade weekend cells with a configurable fill, and optionally band day cells by month with alternating tints.
FR-CB-05
The candybar view shall optionally display a week-number column and a weekday header row, and shall split the strip into side-by-side sections after a configurable number of week rows.
FR-CB-06
The candybar view shall shrink output to its content bounding box by default to avoid large blank margins around the narrow strip.
7.5   Text-mini viewtext-mini
FR-TM-01
The text-mini view shall render a plain-text (non-SVG) mini calendar of month grids honoring weekend style, week numbering, and mini column/row layout.
FR-TM-02
The text-mini view shall mark days bearing events using single-character symbols drawn from configurable symbol sets distinguished by item kind: milestone, single-day event, duration, holiday, and non-working day.
FR-TM-03
When several markings fall on one day, the text-mini view shall resolve the displayed symbol by a fixed precedence among the item kinds.
FR-TM-04
The text-mini view shall render durations by marking their start and end days (and optionally intervening days) with the duration's symbol.
FR-TM-05
The text-mini view shall produce a legend/detail listing mapping each used symbol to its date(s) and task name.
FR-TM-06
The text-mini view shall mark fiscal-period-start days with the period's short name (e.g. P1) when a fiscal calendar is enabled.

8Timeline & Plan Visualizers

These views render events and durations against a continuous time axis or a swimlane grid rather than a day-cell calendar. They share a timeband segmentation engine and the same event style-rule model as the calendar views, while differing in axis geometry and item layout.

8.1   Shared timeband & axis modeltimeline · pit · blockplan · compactplan
FR-TB-01
The system shall segment the date range into labeled time bands by a selectable unit: date, week, month, year, fixed interval (N days), fiscal_quarter, fiscal_period, and per-day icon bands.
FR-TB-02
Each time band shall support a configurable label format, and week/interval bands shall support a configurable week-start and interval anchor/index so band sequences align to a chosen origin.
FR-TB-03
Timeline and plan views shall support stacking multiple time-band rows above and/or below the axis (e.g. a fiscal-quarter row over a month row over a week row).
FR-TB-04
These views shall position items by the user-requested (unadjusted) date range so axis edges match the requested dates exactly, falling back to the week-adjusted range only when no user range is captured.
FR-TB-05
These views shall evaluate event-level theme style rules (per §7.1) to override item color, stroke, icon, and label styling.
FR-TB-06
These views shall honor the common content filters (events, durations, complete, milestones, rollups, WBS, status, notes).
8.2   Timeline viewtimeline
FR-TLN-01
The timeline view shall render a continuous dated axis, horizontal or vertical, with single-day events drawn as leader-connected callout labels and multi-day durations drawn as bars.
FR-TLN-02
The timeline view shall lay out callout labels to avoid collisions and shall place durations into stacked lanes so overlapping spans do not overprint.
FR-TLN-03
The timeline view shall place labels on a selectable side of the axis (primary / secondary / both, alternating chronologically).
FR-TLN-04
The timeline view shall draw a today marker with configurable line length and direction (above / below / both), and configurable label and duration-bar fill opacity.
FR-TLN-05
The timeline view shall draw axis ticks and tick labels derived from a time band, and shall render holiday icons along the axis.
FR-TLN-06
The timeline view shall optionally render fiscal period and/or fiscal quarter band rows above the axis when a fiscal calendar is enabled.
FR-TLN-07
The timeline view shall draw continuation indicators for durations that extend beyond the visible axis range.
8.3   Points-in-Time (PIT) viewpit
FR-PIT-01
The pit view shall render single-day events and milestones along a horizontal or vertical axis (selected by --direction, independent of page orientation) with curved-leader-connected label boxes laid out to avoid collisions.
FR-PIT-02
The pit view shall draw a built-in circle axis marker for events and a built-in diamond axis marker for milestones, with configurable marker size.
FR-PIT-03
The pit view shall support axis ticks with selectable granularity (month, week, fiscal quarter, fiscal period, fixed interval, date, year), configurable tick interval, tick label format, and tick length, and shall allow suppressing ticks and/or tick labels.
FR-PIT-04
The pit view shall support label-side placement (primary / secondary / both) and configurable date placement: inline within the label box, opposite the axis at the marker, or none.
FR-PIT-05
The pit view shall support a today line with on/off control, an override "today" date for forward-dated presentations, and a configurable (or suppressed) today label.
FR-PIT-06
The pit view shall support per-role label-box icons (a default event icon and a default milestone icon by database icon name) with configurable label-icon size and gap, distinct from the fixed axis marker.
FR-PIT-07
The pit view shall support detailed leader geometry control: dash pattern, label anchor (start / center / end), leader length (row spacing), and an end stub segment, and shall support SVG marker-start/marker-end arrowheads on leaders and the axis.
8.4   Block plan viewblockplan
FR-BP-01
The blockplan view shall render a swimlane grid: a left label column plus a time-banded plotting area, with events and durations placed in the lane they match.
FR-BP-02
Swimlanes shall be fully theme-configurable, matching items by resource group, group, resource names (substring), task/notes text (substring), WBS prefix, milestone/rollup flags, event type, and priority (exact / min / max); an unconfigured plan shall default to a single "All Items" lane.
FR-BP-03
Each swimlane shall support per-lane styling — heading fill, label color/alignment, content-area tint, and an upper/lower split ratio governing where events vs. durations are placed within the lane.
FR-BP-04
The blockplan view shall render stacked time-band rows above and/or below the lane region, including NRF-aware fiscal-quarter bands when a fiscal calendar is enabled.
FR-BP-05
The blockplan view shall render durations as labeled bars and events/milestones as markers, with optional icons and inline/appended notes, and shall support configurable vertical reference lines.
FR-BP-06
The blockplan view shall compute the visible day set from the weekend style so non-working columns are handled consistently with the calendar views.
8.5   Compact plan viewcompactplan
FR-CP-01
The compactplan view shall render a compressed activities timeline with duration lines packed into rows above and below a central axis, automatically assigning rows so lines do not visually overlap.
FR-CP-02
The compactplan view shall render milestones as flag markers and shall render time-band rows (including NRF-aware fiscal quarter / fiscal period units).
FR-CP-03
The compactplan view shall render explanatory legends — a milestone list, a holiday list, a continuation legend, and an axis legend — to keep the compressed plot readable.
FR-CP-04
The compactplan view shall indicate durations continuing beyond the visible range and shall shrink output to its content bounding box by default.

9Spreadsheet Outputs

Two commands emit native .xlsx workbooks (via openpyxl) that reproduce the block-plan structure in spreadsheet form, sharing a common column layout and timeband header.

FR-XL-01
The excelheader command shall generate an Excel workbook containing block-plan-style timeband header rows for the requested date range, honoring weekend style, weekend days, country holidays, and an optional theme.
FR-XL-02
The workbook shall use a fixed leftmost label-column block — one column per events-table field (id, status, priority, wbs, rollup, milestone, percent_complete, name, effort, duration, start/end dates, early/late date bounds, predecessors, resource names/group, notes, icon, color, tags) — followed by a reserved continuation-icon column and then one column per visible calendar day.
FR-XL-03
The workbook shall render the requested time bands as header rows (heading label in the label block, segment values across the day columns) followed by a column-header row, and shall set freeze panes so the label columns and band rows remain visible while scrolling (excelheader only).
FR-XL-04
The workbook shall shade day columns for holidays and non-working days and shall apply theme-derived colors to band rows and cells.
FR-XL-05
The excelblockplan command shall additionally write one data row per event/duration in range, populating the label columns from event fields, marking the spanned day columns, applying style-rule-resolved colors/icons, and drawing continuation glyphs when a duration extends beyond the visible range.
FR-XL-06
The excelblockplan command shall honor the full block-plan content-filter set (events, durations, complete, milestones, rollups, notes, WBS, status, empty).
FR-XL-07
Spreadsheet commands shall default their output filenames (excelheader.xlsx, ExcelBlockplan.xlsx) when none is supplied.

10Data Export

A round-trip path lets the filtered event set be written back out as importer-compatible CSV.

FR-EX-01
The exportdata command shall export the filtered set of events/durations overlapping the range to a CSV file.
FR-EX-02
The exported CSV shall use a fixed header whose column names match the event importer's primary aliases (task_name, status, start/finish dates, early/late date bounds, priority, wbs, rollup, milestone, percent_complete, effort, duration, predecessors, resource names/group, notes, icon, color, tags) so the file can be re-imported without relying on fallback aliases.
FR-EX-03
The exporter shall apply the single authoritative content-filtering policy used by the visualizers (events, durations, complete, milestones, rollups, WBS, status, country/holiday exclusion).
FR-EX-04
The exporter shall convert compact YYYYMMDD dates to ISO YYYY-MM-DD form, leaving non-date fields unchanged.
FR-EX-05
The exporter shall default its output filename to exportdata_<startdate>.csv and shall report the number of records written.

11Fiscal Calendars

An optional fiscal-calendar engine overlays retail/period-based fiscal structure on the Gregorian range, feeding labels, colors, and bands across the views.

FR-FC-01
The system shall support an optional fiscal-calendar overlay selectable via --fiscal with types NRF 4-5-4, NRF 4-4-5, NRF 5-4-4, and 13-period.
FR-FC-02
The fiscal engine shall anchor the NRF fiscal year to the Sunday closest to February 1 and shall correctly handle 53-week fiscal years by extending the appropriate period.
FR-FC-03
For any Gregorian date, the engine shall derive fiscal year, fiscal quarter (1–4), fiscal period (1–12 or 1–13), human and short period names (e.g. "Period 1" / "P1"), and period-start / quarter-start flags.
FR-FC-04
The system shall build a per-day fiscal lookup for the calendar range when a fiscal calendar is enabled, for use by all consuming views.
FR-FC-05
The system shall allow the displayed fiscal-year number to be offset relative to the period start year via --fiscal-year-offset (e.g. +1 for a US-federal-style October start), defaulting to an automatic value per type.
FR-FC-06
Weekly and mini-family views shall render fiscal period labels on period-start days and, when --fiscal-colors is set, shade day backgrounds by fiscal period instead of Gregorian month.
FR-FC-07
The text-mini view shall mark period-start days with the period short name, and the timeline view shall optionally render fiscal period and/or quarter band rows (--fiscal-show-periods, --fiscal-show-quarters).
FR-FC-08
Block-plan and compact-plan views shall use NRF-aware fiscal-quarter (and fiscal-period) boundaries for their time bands when a fiscal calendar is enabled.

12Week Numbering

FR-WN-01
Weekly, mini, mini-icon, and text-mini views shall optionally display week numbers (--weeknumbers); the candybar view shows a week-number column by default that may be hidden.
FR-WN-02
The system shall support ISO 8601 week numbering and a custom anchor-based mode selectable via --week-number-mode.
FR-WN-03
In custom mode the system shall number weeks as the count of whole weeks since the anchor (week 1 begins on the anchor date), and shall report week 0 for dates preceding the anchor.
FR-WN-04
The system shall accept a custom week-1 anchor date via --week1-start (YYYYMMDD), which implies week-number display and custom mode for both full and mini calendars.

13Page Layout & Decoration

SVG views share a common page model — paper size, margins, header/footer, watermark, and content-bounding behavior — implemented by a base SVG renderer.

FR-PG-01
SVG views shall support a named paper size (--papersize, case-insensitive) sourced from the database, and page orientation (--orientation portrait/landscape), reporting an error with the available sizes when an unknown size is requested.
FR-PG-02
Paper sizes shall be stored in portrait-canonical form and swapped to the requested orientation, with a database flag indicating sizes that are natively landscape.
FR-PG-03
SVG views shall optionally add page margins (--margin), a page header (--header), and a page footer (--footer), with header/footer heights derived as a configured fraction of page height.
FR-PG-04
The header and footer shall each provide independent left, center, and right text fields laid out as three equal columns within the usable width.
FR-PG-05
Header/footer/watermark/image text fields shall support template variables expanded at render time after the date range is resolved: [now], [date], [startdate], [enddate], and [events]; unrecognized tokens are left intact.
FR-PG-06
SVG views shall support a text watermark with configurable font, color, opacity, rotation angle, and a resize mode of fit (preserve proportions, scale to width) or stretch (scale independently to fill the area), and an image watermark (raster or SVG) with configurable size and rotation; both shall render beneath the page content and respect the shrunk content area when shrink-to-content is active.
FR-PG-07
SVG views shall optionally shade the current date (--shade) and optionally display month names (--monthnames).
FR-PG-08
SVG views shall optionally shrink the SVG width/height/viewBox to the rendered content bounding box (--shrink); compactplan and candybar do so by default.
FR-PG-09
The system shall emit CSS classes (e.g. ec-*) on rendered elements so output can be restyled or post-processed, and shall minify embedded icon/pattern SVG markup (stripping DOCTYPE/comments, collapsing whitespace) to control file size.
FR-PG-10
The weekly, mini, and candybar views shall support per-day decoration with hash styles and named tileable SVG patterns, colorized to a rule color and injected once as deduplicated reusable <pattern> definitions referenced across cells.

14Theming & Color

Appearance is driven by YAML themes parsed into a unified theme model, plus a database-backed color and palette system that themes can reference symbolically.

FR-TH-01
SVG and spreadsheet views shall accept a theme by built-in name (resolved from the bundled themes directory) or by path to a .yaml file (--theme).
FR-TH-02
The system shall validate theme section names and shall warn about (rather than fail on) unknown sections.
FR-TH-03
A theme shall be able to configure general settings, colors, fonts and font sizes, header/footer/watermark, fiscal settings, text/element styles, conditional style rules, per-visualizer settings (weekly, mini, mini-details, timeline, blockplan, compactplan), day-box/day-cell decoration, time-band definitions, and block-plan swimlane definitions.
FR-TH-04
The system shall apply the theme in two passes around automatic font scaling so theme size rules can influence scaling, while explicit theme font sizes take final precedence.
FR-TH-05
Explicit command-line flags that disable a theme-enabled feature shall be re-asserted after theme application so the command line takes precedence over the theme.
FR-TH-06
Themes shall be able to reference database palettes as bulk palettes — month (12), fiscal period (13), group, timeline, block-plan, and compact-plan — resolved into per-element color sets at render time.
FR-TH-07
Themes shall be able to reference individual colors via palette:NAME:INDEX; an integer index shall cycle modulo palette length and a float index in 0–1 shall select a proportional position, with unresolved references degrading with a warning rather than failing.
FR-TH-08
The system shall resolve human-friendly database color names (case-insensitive) to hex values so themes may use names that are not valid CSS/SVG colors.
FR-TH-09
Palette name lookups shall be case-insensitive, and a palette shall be sampleable to an arbitrary count by cycling when shorter than requested.

15Text & Font Rendering

Because there is no viewer-side font fallback, all text is converted to vector outlines, with text measurement driving both layout and glyph placement.

FR-FN-01
The system shall render all text as vector glyph-outline <path> elements rather than embedding or referencing fonts, so output renders identically regardless of fonts installed on the viewer.
FR-FN-02
The system shall position glyphs using actual font metrics with kerning-aware per-character advances, mapping font units to points with the correct vertical flip for SVG.
FR-FN-03
The system shall measure text width from real font metrics and shall provide a shrink-to-fit capability so over-wide text is reduced or truncated to its container.
FR-FN-04
The system shall cache extracted glyphs and font objects to keep repeated text rendering efficient.
FR-FN-05
The system shall automatically scale font sizes to fit the selected paper/page dimensions, with theme-specified sizes able to override the scaled values.
FR-FN-06
The system shall resolve font references through a font registry mapping names to font files, and shall report an error for unknown font names.

16Inspection & Preview Sheets

Utility commands let users discover the named resources available for use in themes, events, and options — both as text listings and as standalone visual preview sheets that do not require rendering a calendar.

16.1   Text listingslisting commands
FR-IN-01
The system shall list available themes, registered fonts (with file paths), paper sizes (grouped by category, with point dimensions), day-box patterns (with tile sizes), icons, colors (with RGB), and palettes (with color counts).
16.2   Visual preview sheetssheet generators
FR-IN-02
The system shall generate an SVG fontsheet previewing every registered font as rendered glyph outlines, with an optional name filter, configurable glyph color, and a full-glyph-set mode that lays out every mapped codepoint.
FR-IN-03
The system shall generate an SVG iconsheet previewing database icons, supporting a name filter, configurable color, and an optional paginated mode with configurable columns, rows, and cell size.
FR-IN-04
The iconsheet generator shall correctly colorize both currentColor-based (stroked) and fill-based icon styles and preserve each icon's native viewBox.
FR-IN-05
The system shall generate an SVG patternsheet previewing day-box patterns tiled in swatches, with a name filter and configurable fill color, scaling oversized tiles to fit.
FR-IN-06
The system shall generate an SVG colorsheet of named color swatches sorted by perceptual hue (HSV), with contrast-aware in-swatch hex labels and a name filter.
FR-IN-07
The system shall generate an SVG palettesheet previewing a single named palette, or, when no name is given, every palette in one sheet, with swatches sorted by perceptual hue.
FR-IN-08
Preview/listing filters that match nothing shall produce a clear error directing the user to the corresponding listing command.

17Diagnostics & Error Handling

The CLI provides graduated logging, embedded provenance metadata, and a defined error/exit-code contract.

FR-DG-01
The system shall provide graduated logging verbosity (-v info, -vv info with module names, -vvv debug) and a quiet mode (--quiet) that limits output to errors.
FR-DG-02
The system shall embed provenance metadata in generated SVG output, including creation date, the invoking command line, and document descriptors (title, author, subject, keywords).
FR-DG-03
The system shall optionally embed the source event data as CSV inside SVG metadata via --embed-data.
FR-DG-04
The system shall validate inputs early — date format, paper size, database existence — and emit user-friendly messages rather than leaking tracebacks from deep in the pipeline.
FR-DG-05
The system shall return distinct process exit codes: 0 success, 1 invalid date/range, 2 database or configuration error, 3 unexpected error (with full traceback logged).
FR-DG-06
The system shall warn when an option is supplied that the selected visualizer does not support (including overflow and SVG-only layout options), and continue rather than abort.
FR-DG-07
On successful generation, the system shall report the output path(s) and summary statistics (event count and overflow count where applicable).

18SVG Output Capabilities

This section enumerates the SVG-level features the graphical views can specify (per-element styling) and include (structural and embedded content). All graphical output is produced through a shared drawing layer, so these capabilities are uniform across the SVG views.

18.1   Drawing primitives & per-element stylingSPECIFIABLE
FR-SVG-01
The system shall emit a defined set of drawing primitives: rectangles, lines, line groups, text, embedded raster images, and nested SVG fragments.
FR-SVG-02
Rectangles shall support fill color, stroke color, independent fill and stroke opacity, stroke width, corner radius (rounded rectangles), and a stroke dash pattern.
FR-SVG-03
Lines and line groups shall support stroke color, stroke width, stroke opacity, and a stroke dash pattern.
FR-SVG-04
Text shall support color, opacity, horizontal anchor (start / middle / end), an optional maximum-width cap that horizontally compresses the text to fit, and an arbitrary SVG transform.
FR-SVG-05
The system shall treat the color tokens none, transparent, and empty as "no paint", omitting fully invisible elements from the output.
FR-SVG-06
The system shall round emitted coordinates to a fixed precision to keep file size and markup noise down.
FR-SVG-07
The system shall apply per-element styling through CSS classes while keeping per-call colors authoritative (emitting them as inline style so they win over class rules).
18.2   Structural & embedded contentINCLUDABLE
FR-SVG-08
The system shall include an SVG <title> (subject + date range) and a <desc> provenance block (creation timestamp, author, date range, paper size/orientation, page dimensions, and invoking command line).
FR-SVG-09
The system shall optionally include the source event data as a <metadata> element containing deflate-compressed, base64-encoded CSV under a dedicated XML namespace, with a row count attribute (--embed-data).
FR-SVG-10
The system shall inject a <style> block from the active theme so the output is restylable via CSS, and shall tag rendered elements with semantic ec-* classes (see §18.3).
FR-SVG-11
The system shall include reusable <defs> content — tileable <pattern> definitions for day decoration and <marker> arrowhead definitions for axis/leader lines — deduplicated by identity so each distinct definition appears once and is referenced by id.
FR-SVG-12
The system shall embed database icons as nested SVG, preserving each icon's native viewBox and colorizing both currentColor-based (stroked) and fill-based icon styles to a requested color.
FR-SVG-13
The system shall embed an external SVG watermark as a nested, aspect-ratio-preserving SVG element, and embed raster watermark images inline (base64) so output is self-contained.
FR-SVG-14
The system shall minify embedded icon/pattern/SVG fragments — stripping comments, DOCTYPE, and XML preamble, and collapsing inter-tag whitespace — without altering significant content.
FR-SVG-15
The system shall support arrowhead markers on the PIT axis and leader lines via marker-start / marker-end, sized in user units and auto-oriented to the line direction.
FR-SVG-16
When shrink-to-content is active, the system shall set the SVG width, height, and viewBox to the exact content bounding box so the artwork carries no surplus page whitespace.
FR-SVG-17
The system shall render glyphs as outline <path> elements (no font dependency) so every produced SVG is fully self-contained and portable (see §15).

AAppendix — Assumptions & Ambiguities

The body of this specification documents behavior as implemented. This appendix flags places where the implemented behavior rests on an unstated assumption, embeds a defaulting decision that may surprise users, or is ambiguous as to designer intent. Each item is worth confirming before the requirements are treated as authoritative. Items are advisory and do not use "shall".

How to read this: A-# items are assumptions baked into the behavior (defaults, magic values, external dependencies). Q-# items are ambiguities where intended vs. implemented behavior is genuinely unclear and a product decision is needed.
