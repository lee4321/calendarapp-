# Changelog

Full git history (oldest first reads bottom-up):

- 2026-09-26 themes: theme inheritance. A theme may `extends:` another (a name or a path) and say only what differs. Sections merge key by key, `unset:` drops a key the parent sets, and `style_rules` entries match parent rules by name: they merge in place, `replace`/`remove` a rule, or insert a new one after the rule the previous entry named. The merge happens at load time (`config/theme_inheritance.py`), so `ThemeEngine`, `parse_theme` and `validate_theme.py` see one ordinary theme. `Julia`, `dark`, `accent` and `vibrant` now extend `corporate` (4,039 → 867 lines; vibrant keeps its own comments). `tools/derive_theme.py` wrote them and refuses any child that does not resolve to exactly the original theme data; each one does, and all 10 themes render byte-identically across the 11 views. `default`, `TJX`, `basic`, `minimal` and `SAMPLE` stay full: default is the reference theme, TJX, basic and minimal reorder the parent's rules, and SAMPLE is the documented example. The two heading papersize rules in seven themes, both named `text:heading — papersize override`, are renamed after their papers, since rule names are now keys
- 2026-09-26 themes: blockplan's section style keys are retired — `grid_color` / `grid_line_width` / `grid_opacity` / `grid_dasharray` (now `line:grid`), `timeband_line_*` (`box:band`, whose stroke still falls back to the grid's), `header_label_color` / `opacity` (`text:heading`), `duration_fill_opacity` / `stroke_*` (`box:duration`), `duration_date_font` / `color` (`text:duration_date`) and `notes_text.font_name` / `font_color` (`text:event_notes`). A dash is taken only from the token itself, never from a fallback. **Breaking:** themes carrying them are rejected; the converter gains `fallback` rows (a key that handed over to another when unset) and three fixes — several rules inserted in one theme no longer shift each other's positions, rule lists written at column 0 (`yaml.dump` style) are indexed correctly, and a conversion that would break the YAML is refused instead of written. Fixes `StyleEngine` applying a rule selected on `visualizer: X` in every view: it ignored the view, so a blockplan-only `box:duration` rule restyled weekly and timeline duration bars; `StyleEngine(rules, visualizer)` now drops rules selected on another view, like `resolve_token` does. The bundled themes render byte-identically across the theme corpus and the timeline corpus
- 2026-09-26 themes: `timeline.name_text` / `notes_text` `font_name` and `font_color`, `timeline.date.font_family` and `timeline.connector_stroke_dasharray` are retired in favour of `text:event_name`, `text:event_notes`, `text:event_date` and `line:grid` (for callout leaders), and `timeline.tick_color`, `timeline.text.font_name` and `timeline_durations.date_font` / `date_color` are removed outright — they were only read after an element style that always has a value, so they never took effect. Label measurement (labella and box packing) now uses the font the renderer draws with, not the retired section font. PIT labels without a `pit.*_text.font_name` fall back to the event text tokens resolved for `visualizer: pit`. **Breaking:** a theme carrying a retired key is rejected; `tools/convert_style_keys.py` gains `override` rows for keys the old code read ahead of the token (the PIT fallbacks), writing those rules even when the token already sets the attribute, and stays idempotent. The bundled themes were converted and render byte-identically across the theme corpus (10 themes x 11 views) and the timeline corpus (2,348 files)
- 2026-09-26 themes: `mini_calendar.grid_line_color` / `grid_line_width` / `grid_line_opacity` / `grid_line_dasharray`, `milestone_stroke_width` / `milestone_stroke_opacity` and `cell_font` are retired; mini, mini-icon and candybar take the grid from `line:grid`, the milestone circle from `icon:milestone` and the day-number font from `text:day_number` (falling back to the `ec-grid-line` / `ec-day-number` element styles). mini and mini-icon now share one grid-line resolver, so the two no longer disagree when a theme sets only one source. **Breaking:** a theme still carrying one of these keys is rejected; `tools/convert_style_keys.py --in-place` converts it (now idempotent: a second run adds nothing). The bundled themes were converted; the only render change is the corner event icons moving 0.25 pt, because their inset now follows the grid width actually drawn rather than the retired key
- 2026-09-26 themes: `weekly.day_box.stroke_color` / `stroke_opacity` / `stroke_width` / `stroke_dasharray` are retired; the weekly day box takes its stroke from the `box:cell` token alone (falling back to the `ec-cell` element style). **Breaking:** a theme that still carries one is rejected; `tools/convert_style_keys.py --in-place` moves its values into a `box:cell` rule selected on `visualizer: weekly`, writing out any old built-in default that was in effect, so the theme renders as before. The bundled themes were converted this way and render byte-identically.
- 2026-09-26 themes: element styles always come from tokens. With no theme, or a theme without `style_rules`, every `ec-*` element now takes its style from `config/element_catalog_defaults.yaml` — the source that already filled the tokens a theme leaves undefined — instead of from `CalendarConfig` fields. **Breaking:** the 48 section keys that only fed those fields are removed (among them `header.*.font_family`/`font_color`, `footer.center.*`, `weekly.day_names.*`, `weekly.week_numbers.*`, `weekly.day_box.fill_*`/`number_*`/`font_color`, `weekly.name_text`/`notes_text` font name/color/opacity, `mini_calendar.title_font`/`title_color`/`day_color`, `colors.mini_calendar.day_color`, the timeline axis/tick/today/label dasharray and color keys, `blockplan.vertical_line_*`, `watermark.color`, `overflow.color`). In a theme with `style_rules` none of them had any effect, and the 10 bundled themes render byte-identically; set the matching token instead. A theme that still carries one gets the usual "not read by any visualizer" warning. Themeless runs change to the catalog defaults (a white page background among them).
- 2026-09-19 patterns: scope each tile's ids to its own `<pattern>` def. Tiles are authored as standalone documents, but `extract_pattern_inner()` inlines their content into one shared `<defs>`, ids and all. The 112 EMF-derived `stars*` tiles each carry the same six — `defs2`, `layer1`, `base`, `grid8`, `metadata5`, and the empty 6x6 hatch-base `EMFhbasepattern` that Inkscape's EMF import leaves behind — so `patternsheet --filter stars1` emitted 24 copies of each. That was invalid markup rather than a wrong render, because no tile in the table references its own ids and the colliding ones are inert leftovers; it would stop being harmless the moment a tile painted with an internal reference, where a second copy would silently resolve to the first tile's element with no error to trace. `scope_pattern_ids()` prefixes every declared id with the def id (already unique per pattern and color) and repoints the `url(#…)` / `href="#…"` / `xlink:href="#…"` references that resolve to it, leaving references to undeclared ids alone so a reference out to the containing document still works. All 350 tiles in one document now yield 869 distinct ids with no duplicates and no dangling references. Four refcorpus files move — the default theme's `diagonal-stripes` is the only shipped theme pattern carrying ids, while dark's `wiggle` and corporate's `circuit-board` carry none — and the change is markup-only: un-prefixing the new output reproduces the old byte for byte, and all four render pixel-identically
- 2026-09-19 patterns: repaint every tile's ink, not just the literal black fills. `colorize_pattern_svg()` rewrote only `fill="#000000"`, `fill="#000"` and `fill="black"`, so of the 350 tiles in the `patterns` table just 130 obeyed the color a `style_rules` `patterncolor`, a theme rule or `--color` asked for. A survey of the rest found four more ways the authoring tools declared the same monochrome ink: 111 Inkscape `stars*` tiles use `style="fill:#000000"`, 27 Serif `dingbat*` tiles use `style="fill:rgb(35,31,32)"`, 56 use `stroke="currentColor"` and 28 `fill="currentColor"` — and `currentColor` inside a `<pattern>` def resolves against the def rather than the element carrying `fill="url(#pat-id)"`, so those never took a color at all. Since no tile in the table mixes two ink values, the fix is a rule rather than a longer literal list: every paint declaration that draws something is rewritten, in both the attribute and `style="…"` forms, while `none`/`inherit`/`transparent` are left alone so hollow shapes stay hollow and the hyphenated `fill-rule`/`stroke-width` family is never mistaken for paint. `pattern_def_xml()` also emits the color on its wrapper `<g>`, because `extract_pattern_inner()` drops the source `<svg>` element and with it the root-level `fill="currentColor"` that 25 tiles rely on; the wrapper sets `fill` but deliberately not `stroke`, since an unset stroke defaults to `none` and setting it would outline shapes that were never stroked. All 350 tiles now recolor except `stars65`, which is an embedded base64 PNG (and at ~950 KB by far the largest row): `pattern_is_recolorable()` detects raster artwork, `patterns` marks it `[fixed]` and the sheet labels it `(fixed)`. `_generate_patternsheet_svg()` drops its duplicate def builder and calls `pattern_def_xml()`, so a swatch now shows the grain and the color a day box will actually get
- 2026-09-19 patterns: auto-normalize decoration tile sizes so large patterns read as texture instead of one crop. Native tiles in the `patterns` table span 16 pt to 1920 pt and `pattern_def_xml()` emitted them at native size under `patternUnits="userSpaceOnUse"`, so against a 384 x 54 pt weekly day box 242 of the 350 patterns never repeated vertically and 105 never repeated in either direction — the `circles*` family (95 tiles at 1920 pt) filled a whole page with a single tile. `renderers/svg_patterns.normalize_tile_scale()` now shrinks any tile whose largest dimension exceeds a target down to it, wrapping the artwork in `<g transform="scale(s)">` and shrinking the pattern's reported width/height by the same factor so it still tiles seamlessly; normalization is deliberately shrink-only, since the 26 tiles already at or below the target read correctly as-is. The target is `hash_pattern_target_size` (default 18 pt, `0` restores native tiling) with `hash_pattern_scale` as an extra multiplier, both settable per theme as `weekly.day_box.hash_pattern_target_size` / `.hash_pattern_scale` and applied uniformly by the weekly, mini and PIT renderers. `patternsheet` previews the normalized grain rather than a blown-up crop and gains `--tile-size` for trying other values; `patterns` prints native and normalized sizes side by side. Every pattern-bearing page moves in the refcorpus, which is the intended change
