Gantt Visualization — Questions To Be Addressed

Review of gantt_chart_requirements.txt against the existing codebase (visualizers/blockplan/, visualizers/pit/, shared/rule_engine.py, shared/timeband.py, config/element_catalog.yaml, cli/args.py, and the events schema), plus the three example images. Items marked blocking must be settled before a plan can be written; the rest have a suggested default that can be adopted as a stated assumption.

A. Data availability blocking

The columns the spec is built around are empty in the current database. Over the 105 rows in events: 0 non-empty predecessors, 0 non-empty wbs, 0 earliest_start_date/latest_*, and every percent_complete is 0.0. There are 9 rollups and 22 milestones.
  1. Where does dependency / WBS / float data come from — a new import (MS Project XML, P6, CSV)? Can you supply a sample file so there is a real dataset to develop and test against? Without one, the three headline features (arrows, float bars, progress) are untestable.
  2. predecessors is free text. importers/import_events.py:108 states that predecessors/successors reference source_id, not events.id — please confirm. What syntax must be parsed: MS Project style "12FS+3d,15SS" (comma list, link type, lag), or a bare id list? Suggested: parse comma-separated <id>[FS|SS|FF|SF][±<n>d]; a bare id means FS; lag ignored for geometry.
  3. duration and effort are REAL, alongside text twins duration_text and effort_text. Which does the column render, and with what unit suffix ("10 days")?
  4. rollup and milestone are integers. In the task table, render as what — a checkmark icon, "Yes"/blank, or nothing (indentation alone conveys rollup)? Suggested: themeable icon, blank when false.
  5. The default column list has no ID column, but example2 shows Predecessors/Successors columns that are only readable with one. Should id/source_id, predecessors, and successors be available as columns (just not defaults)?

B. Task-list rows and sorting

  1. Are rollup rows actual event rows (rollup=1), or should parent rows be synthesized from the WBS hierarchy when no such row exists? Suggested: only real rows; no synthesis.
  2. WBS sort must be segment-wise numeric (1.10 after 1.9), not lexical — confirm. And where do empty-WBS rows go: interleaved by start_date, or grouped after all WBS rows? Suggested: grouped after.
  3. Is indent depth the count of WBS segments? What indents a child whose wbs is empty? Suggested: depth from segment count; empty WBS = depth 0.
  4. Row height: fixed and uniform (wrap limited to N lines, then truncate), or auto-expanding to fit wrapped notes? Auto-expansion breaks a clean grid and complicates paging. Suggested: uniform height, per-column max_lines, ellipsis.

C. Pagination blocking

No precedent exists in the codebase: both blockplan and compactplan explicitly never overflow (visualizers/blockplan/renderer.py:215 — "blockplan never overflows"). A Gantt of 200 tasks over 18 months cannot fit one sheet.
  1. Vertical overflow: paginate into multiple pages repeating the column header and timescale, auto-shrink the row height to fit, or truncate? Suggested: paginate, repeating header + timescale.
  2. Horizontal overflow (long date range): paginate across pages repeating the task table on each, force-fit the whole range onto one width, or require the caller to narrow --start/--end? Suggested: force-fit to one page width for v1; paginate later.
  3. Does output file naming follow the existing _overflow.svg convention, or _p2, _p3…?

D. Timescale and weekends

  1. weekend_style = 0 currently removes non-working columns entirely (blockplan's _visible_days). That makes the x-axis non-linear, so bars must be laid out per visible-day column rather than by linear date interpolation. Confirm that is the intent (example0 shows exactly this M–F axis), rather than "show all days, shade the weekends".
  2. When weekends are hidden, are country holidays still columns that get shaded, or also removed from the axis? Suggested: kept as columns and shaded — otherwise the axis silently changes per country.
  3. Timescale extent: driven by the existing --start/--end calendar range, or auto-fit to the min/max dates of the filtered task set? Suggested: the calendar range, as every other view does.
  4. The spec covers bars starting before the scale. What about bars ending after it — hard clip, or clip with a continuation arrow (compactplan already has ec-continuation-icon)? Suggested: clip with a continuation marker at both ends.
  5. Reuse the blockplan band configuration verbatim (gantt_top_time_bands / gantt_bottom_time_bands, same band dicts), or define a new schema?

E. Bars, progress, floats, milestones

  1. Percent-complete: is the ratio measured against calendar span or working-day span? They differ once weekends are dropped. Suggested: working days, so the line matches the drawn bar.
  2. Do rollup brackets also get a progress line and float bars, or bar only? Suggested: bracket only.
  3. Is the rollup bracket drawn from the rollup row's own start_date/end_date, or from the min/max of its WBS children? The two can disagree. Suggested: the row's own dates; fall back to children only when the row's dates are empty.
  4. deadline is in the default column list. Should it also render a marker on the chart (the usual inverted triangle/arrow), or stay text-only? The spec does not say.
  5. Single-day events landing on a hidden weekend or holiday: skip, snap to the next visible working day, or force the column in? Suggested: snap forward, and log it.
  6. Milestone anchor date when start_date ≠ end_date — start, or end? Suggested: end_date, per MS Project convention.
  7. Float bars when earliest_*/latest_* are empty (100% of current rows): draw nothing at all — confirm.

F. Dependency arrows

  1. Support all four link types (FS/SS/FF/SF) with correct anchor points, or FS-only for v1? Suggested: FS-only; other types fall back to FS geometry.
  2. Backward links (successor starts before the predecessor ends) need routing around the bar. Accept a simple three-segment dogleg that may cross other bars, or invest in collision-avoiding routing? Suggested: simple dogleg; routing quality is a later pass.
  3. When a predecessor is filtered out, off-page, or outside the date range: drop the arrow silently, or draw a stub indicating an off-chart dependency? Suggested: drop, with a debug log.
  4. On by default, or opt-in via CLI flag / presence of a style rule? The document says "via theme definition style_rules", which reads as opt-in — confirm.

G. Theming and configuration architecture

  1. (blocking) Column definitions — which columns, order, width, justification, wrap/truncate, sort order, date format — are layout config, not visual style, whereas the unified style_rules schema is match/apply_to/style. Should these live in a dedicated gantt.columns: theme section, the way blockplan.swimlanes does, with style_rules handling only fill/stroke/font? Strongly suggested: yes — forcing column layout through style_rules fights the schema.
  2. 'dd' is not an Arrow token: Arrow supports ddd/dddd, and format('dd') returns an empty string (verified). Confirm dd should be a custom pre-pass token meaning the two-letter weekday ("Mo", "Tu"), and whether it applies to gantt columns only or to all date formatting app-wide.
  3. Which CLI flags are wanted beyond the shared set — e.g. --columns, --no-dependencies, --today-date? These must go in _CLI_CONFIG_OVERRIDES in cli/config_assembly.py to survive theme precedence.
  4. Today line: mirror the PIT keys as gantt_show_today_line / gantt_today_date (same semantics — YYYYMMDD override else wall clock, suppressed when outside the range), or read the pit_* keys directly? Suggested: mirror as gantt_*.
  5. Subcommand name — gantt? Any expectation of an Excel counterpart (excelgantt, as excelblockplan mirrors blockplan)? Assumed out of scope.
  6. New ec-* classes must be registered in config/element_catalog.yaml (CI enforces this). Proposed additions: ec-task-cell, ec-column-header, ec-row-band, ec-progress-line, ec-dependency-arrow, ec-float-bar, ec-rollup-bracket. Any naming preference, and should any of them reuse an existing token rather than getting a new one?
  7. Do all 19 theme YAMLs need a gantt: section, or code-level defaults plus a section in default.yaml/SAMPLE.yaml only? Suggested: the latter.

H. Scope check

  1. The document says "only those [features] that are completely unique should be planned." My reading of what is genuinely new: the task-table/column grid, dependency-arrow routing, progress lines, float bars, and rollup brackets. Reusable as-is: timebands, weekend/holiday day classification, RuleEngine, today-line logic, content filters, text/glyph rendering, and paper/orientation handling. Does that split match your expectation, or is there existing code you expect to be reused that this misses?
Minimum to unblock: A.1, A.2, C.10, and G.29. Everything else can proceed on the suggested defaults, recorded as explicit assumptions in the plan.
