Design Specification

A Textual TUI for EventCalendar

A terminal UI (built on textual) that drives every visualization, all data filtering, full command-line parameter selection, and event-data import — as a thin, introspection-driven front end over the existing ecalendar.py argparse layer.

01What the UI must cover

Grounded in the real CLI surface from ecalendar.py and importers/import_events.py. The tool is a subcommand CLI with three classes of command:

ClassSubcommandsNotes
Calendar views
date-ranged, full option set		 weekly mini mini_icon candybar text-mini timeline pit blockplan compactplan excelheader excelblockplan exportdata Share begin/end + Database / Output / Layout / Header-Footer / Watermark / Content-Filtering / Fiscal / Logging groups
Reference sheets / listings themes papersizes patterns icons colors palettes palettesheet iconsheet patternsheet colorsheet fonts fontsheet DB-driven enumerations — also the source of truth for pickers
Import import_events.py (separate entry) file/dir import, --generate scripts, --replace, --dry-run, history --list/--remove
The design hinges on one fact: the listing subcommands (themes, papersizes, fonts, icons, colors, palettes, patterns) are exactly the value-spaces for the pickers. The TUI calls them to populate dropdowns instead of hardcoding — so the UI never drifts from the DB/registry.

02Architecture

A single Textual App that is a GUI front end over the existing argparse layer — it never reimplements rendering logic; it builds an argv and shells out (or imports ecalendar.main() in-process). This keeps the TUI thin and immune to calendar-engine changes.

tui/ app.py # CalendarTUI(App) — screen stack, global bindings, DB path spec.py # ARG SPEC: introspected from the argparse parser (single source of truth) registry.py # queries listing subcommands -> picker option lists (cached) runner.py # builds argv, runs ecalendar/import in worker, streams stdout/log screens/ home.py # command launcher (the 12 views + import + sheets) builder.py # the big parameter form (tabbed by arg-group) filters.py # Content-Filtering panel (shared widget, embedded in builder) import_hub.py # Import Hub: events / special days / holidays / content import_wizard.py# shared file+dry-run+history wizard, parameterised per importer importers_spec.py # adapters: argv builders for import_events/specialdays/holidays/… preview.py # render result: SVG->terminal image / text output / log tail pickers.py # modal selection lists (theme/paper/font/icon/color/palette) widgets/ daterange.py # begin/end with validation + presets (this quarter, FY, etc.) argfield.py # one widget per arg, driven by spec (bool->Switch, choices->Select…)
Key idea — spec.py is generated, not written. Walk the existing build_parser() _action_groups/_actions once at startup. Each Action already carries dest, option_strings, type, choices, default, help, and nargs. That metadata deterministically maps to a widget.

Because it's introspected, new CLI flags appear in the UI automatically — no maintenance. The help string becomes the field's tooltip/description.

The Filters tab is the "data filtering" surface

It's the highest-value part — a shared widget reused by every view, the importer's dry-run, and export:

┌─ Filters (Content) ───────────────────────────────────────────┐ │ Events [✓] single-day [✓] durations [ ] only milestones│ │ [ ] only rollups [ ] ignore 100% complete │ │ Status [active ✓][draft][on-hold][cancelled][archived][all]│ │ WBS [ 1.2.*, !1.2.9, 3.** ] │ │ Notes [ ] include notes in titles │ │ Holidays Country [US,CA ▾] Weekend-days [Sat,Sun ▾] │ │ Date scope [✓] empty(blank) [✓] shade today [ ] overflow page│ └───────────────────────────────────────────────────────────────┘

WBS gets live validation against the grammar (*, **, !, dot-segments); --status is a multi-select chip row mapping to the comma list; --country and --weekend-days are multi-selects backed by the same parsing the CLI does.

04Data import hub

Importing is a separate entry-point family, not part of ecalendar.py. The TUI gives it its own top-level Import Hub with one wizard per data type. Three of the importers (import_events.py, import_specialdays.py, import_holidays.py) share nearly the same grammar — file/dir input, --dry-run, --replace, --skip-errors, history --list, removal, and --log-file/--log-level — so they are driven by one shared wizard component parameterised per importer.

┌─ Import Hub ──────────────────────────────────────────────────┐ │ Pick a data type to import: │ │ ▸ Events project tasks / durations / milestones │ │ ▸ Special days company nonworkdays, observances, custom days │ │ ▸ Holidays government holidays (CSV, by country) │ │ ▸ Content · icons · patterns · colors (reference data) │ │ │ │ [Enter] open wizard [h] history [Esc] home │ └───────────────────────────────────────────────────────────────┘

4.1 — Events (full import_events.py functionality)

Generator-only fields (--start-date/--end-date/--param) are disabled unless Generator source is chosen — mirroring the CLI's own parser.error guard so the UI can't build an invalid argv.

4.2 — Special days (import_specialdays.py)

Same shared wizard, plus the two fields unique to special-day imports — --country and --language — and a column-aware dry-run that knows the special-day schema:

┌─ Import · Special days ───────────────────────────────────────┐ │ Source [ SpecialDays/company.xlsx ][📁] │ │ Target --database [ calendar.db ] --user-id [1] │ │ Tagging --country [US ▾] --language [en ▾] │ │ Mode [ ] --replace [✓] --dry-run [ ] --skip-errors │ │ ─────────────────────────────────────────────────────────────── │ │ Detected columns: name ✓ start_date ✓ nonworkday ✓ icon ✓ │ │ daycolor · pattern · patterncolor · tags · fullday · notes │ │ Dry-run: 11 rows OK · 0 errors │ │ [Import] [View history] [Remove…] [Esc] │ └───────────────────────────────────────────────────────────────┘

The dry-run panel renders the accepted special-day columns (name, start_date/end_date, company, nonworkday, fullday, starthour/endhour, icon, daycolor, pattern/patterncolor, tags, visible, notes) and flags which were matched from the file's headers — so column-aliasing problems are caught before import. These are the company nonworkdays/observances that the Filters panel (§3) and holiday-color logic consume downstream.

4.3 — Holidays & reference content

The hub also reaches the rest of the importer family so the whole DB can be populated from one place:

Holidays · import_holidays.py

CSV-by-country government holidays. Shared wizard with --country/--language; note this importer uses --clear (wipe all) rather than --remove, so its history panel shows a Clear-all action instead of row removal.

Icons · import_icons.py

Folder of .svg → icon table. Folder picker + replace toggle; feeds the icon pickers in §2.

Patterns · import_patterns.py

Folder of .svg → patterns table (day-box decoration). Folder picker + replace toggle.

Colors · import_rcairo_colors.py

Rcairocolors.csv → colors table via --db/--csv. Two path inputs and a run button.

4.4 — Import history (shared)

Events and special days both maintain an import_history; the wizard exposes it as a live table backed by each importer's --list, with row-select driving --remove:

┌─ Import history ──────────────────────────────────────────────┐ │ ID File When Rows Type [ ]select │ │ 12 PI7.xlsx 06-20 14:02 118 events │ │ 11 company.xlsx 06-19 09:31 11 specialdays │ │ 10 PI6.csv 06-12 16:40 97 events │ │ ─────────────────────────────────────────────────────────────── │ │ Remove [ 10-12 ] (single · 1-5 · 1,3,5 · 5- · all) [ ] --force│ │ [Remove selected] [Refresh] [Esc] │ └───────────────────────────────────────────────────────────────┘

--dry-run runs automatically on file selection and gates the real Import button — turning a blind CLI flag into a guardrail. The --remove field accepts the full range grammar (3, 1-5, 1,3,5, 5-, all); --force skips the confirmation modal.

05Execution model

Worker, not blocking

runner.py runs the build in a Textual @work(thread=True) worker, streaming stdout/log into a RichLog. The UI stays responsive; --verbose maps to a verbosity slider.

Two run modes

In-process (ecalendar.run(argv)) for speed, or subprocess for isolation. The subprocess path uses uv run — this project runs Python via uv, never raw python.

Live command bar

Always shows the exact argv being assembled — the TUI is a teaching tool for the CLI, and "copy command" lets power users graduate to the shell.

Presets

Any builder state serializes to a named JSON preset (a dict of dest→value); "re-run last" and saved presets live on Home.

Preview

SVG output rendered inline via a terminal image protocol (Kitty/iTerm/Sixel) with text fallback; text-mini/exportdata/listing commands show their text straight in a RichLog.

Pickers from the DB

Theme/paper/font/icon/color/palette modals are populated by calling the listing subcommands, so values match what the engine can actually render.

06Why this shape

  1. Introspection over duplication — the form is generated from the parser, so 100+ flags and any future ones are covered for free, and help text is reused as documentation.
  2. Listing subcommands as pickers — the UI's value-spaces come from the same DB/registry the engine uses, so themes/fonts/icons/colors never go stale.
  3. Shared Filters widget — "all data filtering" is one component reused across views, import dry-run, and export, instead of rebuilt per screen.
  4. Thin front end — it builds argv and shells/calls into existing code; zero calendar logic is reimplemented, so the engine stays the single source of truth.
  5. One wizard for a family of importers — events, special days, and holidays share a grammar, so they share a component; per-importer differences (--country/--language, --clear vs --remove, generator mode) are just adapter config, and dry-run gates every real write.
