Evaluation of security.md

A solid skeleton but it's a feature plan, not a security plan — the threat model and several core controls are missing. Below are the gaps grouped by severity.

Critical gaps

1. No auth on the admin tools (tools/authorize.py, tools/defaults.py). Anyone with shell access can add-user, resetpassword, or deactivate any account — including their own privilege escalation. There's no notion of an admin role or a "must authenticate as admin before invoking these subcommands" gate. resetpassword in particular has no current-password check.

2. Password hashing is under-specified. "hashlib.pbkdf2_hmac() + random salt" leaves:

  • Algorithm (must be sha256 minimum), iteration count (OWASP 2023+: ≥600k for SHA-256), salt length (≥16 bytes from secrets.token_bytes).
  • Storage format. Recommend a composite string pbkdf2_sha256$<iter>$<salt_b64>$<hash_b64> so iterations can be upgraded without breaking existing hashes.
  • verify_password must use hmac.compare_digest (timing-safe), not ==.
  • Consider argon2-cffi instead — PBKDF2 is acceptable but argon2id is the modern default.

3. Password on CLI (--password / -pw). Leaks to shell history, ps aux, process accounting, CI logs. Recommend:

  • Drop the flag in interactive paths; always prompt via getpass.
  • For automation, read from $CALENDARAPP_PASSWORD env var or --password-stdin (the docker/git pattern).
  • If you keep --password for tests, gate it behind --password only when stdin is not a TTY, and document the risk.

4. Default admin admin / changeme. No first-login rotation requirement. Combined with seeding into calendar.db (which is checked into the repo per git status), this would ship default creds. Recommend: refuse to authenticate if password_hash matches the seeded "changeme" hash until rotated, or generate a random password at seed time and print it once.

5. Authorization is read-only. Plan filters get_all_events_in_range and special-day queries but doesn't touch event ingest (importers/), update, or delete paths. A user with DB access can still write events under another user_id. If the threat is "users on shared host", you also need write-side checks; if the threat is only "shared SVG output", say so explicitly.

Design issues

6. Inconsistent --userid vs --username vs --user-id. Step 5a says --username, 5b says --userid, Step 6 uses --user-id, verification uses --userid 1. Pick one — recommend --username for login (humans don't memorize IDs) and --user-id only in admin tooling.

7. specialdays.company is free-form TEXT, not company_id FK. Plan filters by config.company_name (Step 4, Step 7). A company rename silently orphans rows; misspellings silently grant or deny access. Recommend:

  • Add company_id INTEGER REFERENCES companies(id) to specialdays, backfill, and filter by ID.
  • Keep company text as a display-only legacy column or drop it after migration.

8. specialdays.user column is ignored. Plan only filters by company but schema already supports per-user special days. Either filter by user_id too or drop the column.

9. Username uniqueness is global. UNIQUE(username) across the table prevents two companies from both having "alice". Decide: email-as-username (global unique is fine) or UNIQUE(company_id, username) (multi-tenant scoping).

10. SQLite FKs are off by default. REFERENCES companies(id) does nothing unless PRAGMA foreign_keys = ON is set on every connection. Add this to CalendarDB's connect path.

11. Hard delete vs soft delete. Soft delete exists (active=0); the plan also exposes delete --user-id / delete --company-id with no cascade rules. What happens to events owned by a deleted user? Recommend: drop hard-delete from the tool, or require --force plus explicit cascade behavior.

12. CSV import is in the "context" bullet at the top but never specified. Format, password handling (column? generated? forced-rotate?), error/duplicate handling, dry-run mode — all undefined.

Missing controls

13. No rate limit / lockout. Brute force against --password is unbounded. Add failed_attempts and locked_until columns on users, lock after N failures with exponential backoff.

14. No audit columns. Add created_at, updated_at, last_login_at, password_changed_at to both tables. Optional but recommended: an auth_audit_log table for admin actions (who reset whose password, who deactivated whom).

15. No self-service password change. Only admin-driven reset. Add ecalendar.py change-password or similar.

16. company_defaults.logo and font path fields. If these are read from disk at render time, you have a path-traversal vector — a malicious admin could point logo at /etc/passwd and exfiltrate via SVG. Constrain to a known directory or require resource IDs.

Smaller nits

  • 17. Step 4 says "append AND user_id = ? when set" — explicitly call out: use parameterized queries, never f-strings, even for the optional clause.
  • 18. events.user_id is currently NOT NULL (per schema dump) — the seed script's "update orphan events" is a no-op unless there's a sentinel value. Verify and adjust.
  • 19. The companyspecialdays view is SELECT * FROM specialdays — it adds nothing. Either make it actually filter (requires per-session view, not a great fit for SQLite) or remove it and query the table directly.
  • 20. Authorization on the exportdata subcommand (line 169) deserves a callout — bulk export is the highest-value target for data exfiltration; consider logging every export with user_id + range.
  • 21. Path note: memory says top-level db_access.py, plan says shared/db_access.py. Code is at shared/db_access.py — confirm and update memory if the file moved.
  • 22. Tests should include explicit negative authorization tests: user A authenticated, requests range containing user B's events, asserts B's events are absent from output (not just from the DB query).

Library support

No single module satisfies most of the gaps above — admin role, authorization gates, write-side checks, audit log, FK pragma, CSV import policy, and the threat model are all application-level work. The one clean library win is password hashing.

  • passlib — directly addresses gap #2. passlib.hash.pbkdf2_sha256 produces exactly the composite pbkdf2_sha256$<iter>$<salt>$<hash> format recommended above, handles timing-safe verify, and supports CryptContext for iteration upgrades without breaking existing hashes. Switching to argon2 later is a one-line config change.
  • argon2-cffi — alternative if you want to skip PBKDF2 and adopt argon2id directly. Smaller surface area than passlib.

Stdlib already covers adjacent items: hmac.compare_digest (timing-safe compare for gap #2), secrets.token_bytes (salt generation), getpass.getpass (interactive prompt for gap #3).

For the remaining gaps:

  • Rate limit / lockout (#13) — hand-rolled against the users table. Web-oriented libraries (limits, slowapi) assume a framework and don't fit a CLI.
  • Admin role, authz filtering, audit log, FK pragma, logo path traversal (#1, #5, #10, #14, #16) — application code in the CLI and shared/db_access.py.
  • If auth ever moves into a web context, authlib or flask-security-too bundle more of this, but that's a larger commitment than the CLI tool this plan describes.

Recommendation: adopt passlib for #2, use stdlib for #3, and treat everything else as design work.

Recommended additions before implementation

  1. Write a one-paragraph threat model: who the adversary is (other authenticated users? shell users on the same host? someone with the .db file?), what they're trying to access, and which of those threats this plan addresses vs. accepts. Several gaps above resolve themselves once that's pinned down.
  2. Decide on admin role (new users.is_admin column or a separate admins table) and gate the admin tools on it. Without this, Steps 6a/6b are unsafe to ship.
  3. Specify the password hash format string and iteration policy in Step 2.
  4. Replace company_name filtering with company_id filtering end-to-end (Steps 3, 4, 7).
  5. Decide and document the --password policy (prompt-only, stdin, or env var).
